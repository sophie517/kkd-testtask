# 06 — Testing and Quality

> **Примечание:** Реализация тестирования будет выполнена на финальном этапе разработки. Ниже — план тестирования, не реализация.

## План тестирования (реализация на финальном этапе)

### Unit-тесты (обязательно)

**Validation Engine** — каждое из 4 правил тестируется независимо от Spring и базы данных.

Для каждого правила проверяем:
1. **Обнаружение нарушения** при некорректных данных.
2. **Отсутствие нарушения** при корректных данных.
3. **Применение только к активным целям** — архивные цели не проверяются.
4. **Граничные случаи** — минимум для двух правил (требование бизнес-задания).

| Правило | Граничные случаи |
|---|---|
| `GOAL_NO_OWNER` | Цель с `owner_id = null` vs `owner_id = "EMP-001"` |
| `GOAL_NO_KR` | Активная цель без КР vs с одним КР |
| `KR_WEIGHTS_SUM` | Сумма = 100, 99, 101, 99.99 |
| `CASCADE_NO_PARENT` | Цель корневого подразделения vs цель дочернего без родительской цели |

### Тестирование дельты

Логика расчёта дельты тестируется отдельно от Service Layer.

Проверяем три сценария:
1. **new** — нарушение есть в текущем прогоне, но отсутствует в предыдущем.
2. **persisting** — нарушение присутствует в обоих прогонах.
3. **resolved** — нарушение было в предыдущем прогоне, но отсутствует в текущем.

Идентичность нарушения определяется парой `rule_code + object_id`.

### Тестирование первого прогона

Первый прогон — критический кейс: сравнения с предыдущим прогоном нет.

Проверяем:
1. `compared_to` = `null` в ответе API.
2. `previous` = `null` (не `0`) для всех метрик.
3. `delta` = `null` (не `0`) для всех метрик.
4. `trend` = `null` (не `better` / `worse` / `neutral`).
5. Все проблемы первого прогона считаются `new` — нет `persisting` и `resolved`.

### Интеграция дельты с Service Layer

Проверяем, что Service Layer корректно рассчитывает дельту при запуске нового прогона.

### HTTP-тесты

| Сценарий | Ожидаемый статус |
|---|---|
| Успешный запрос API | 200 OK |
| Неизвестный `run_id` | 404 |
| Неизвестный `unit_id` | 404 |
| Некорректные параметры | 422 |

Формат ошибки — единый:
```json
{"error": {"code": "...", "message": "..."}}
```

Проверяем не только HTTP-статус, но и структуру JSON ошибки.

## Приёмочные критерии (план)

- [ ] Все unit-тесты проходят без ошибок.
- [ ] Каждое из 4 правил тестируется на обнаружение нарушения и отсутствие нарушения.
- [ ] Граничные случаи проверены минимум для двух правил.
- [ ] Логика дельты протестирована отдельно и в интеграции с Service Layer.
- [ ] HTTP-статусы и формат ошибок проверены.
- [ ] Liquibase: `update → rollback → update` проходит успешно.
- [ ] Структура БД после повторного `update` соответствует актуальной версии миграций.
- [ ] `mvnw clean package` завершается успешно.
- [ ] `mvnw test` — все тесты проходят.
- [ ] `docker compose up` — приложение запускается, Liquibase применяет миграции автоматически.

## Не входит в scope тестирования v1

- Интеграционные тесты с Testcontainers.
- Web-тесты контроллеров (`@WebMvcTest`).
- Покрытие кода тестами (code coverage metric).
- Нагрузочные тесты.
