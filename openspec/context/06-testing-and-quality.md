# Тестирование и приёмка

Обновлено: 2026-11-08.

## Минимум из задания

JUnit 5: минимум четыре предметных сценария — два правила на граничных данных,
расчёт метрики и расчёт дельты. Поднимать HTTP для тестов не требуется.
Тесты пишем вместе с соответствующей логикой, не переносим все проверки на финальный этап.
Существующий contextLoads отключает БД и Liquibase и подтверждает только загрузку
skeleton. Он не заменяет эти сценарии и не доказывает работоспособность миграций.

## Небольшой целевой набор

1. KR_WEIGHTS_SUM: 100.00, 99.99, 100.01; точное сложение 33.33 + 33.33 + 33.34;
   без КР нарушение веса не создаётся.
2. CASCADE_NO_PARENT: корневое подразделение, отсутствующий родитель,
   активная цель непосредственного родителя, неверный уровень и архивный родитель.
3. Метрики: цели дочерних подразделений включаются, цель с несколькими проблемами
   учитывается в B один раз; N = 0 и округление проверены.
4. Дельта: new/persisting/resolved; идентичность по rule_code + goal_id,
   а не issue.id. Первый прогон возвращает null для всех значений сравнения.

В этих же небольших тестовых наборах проверить GOAL_NO_OWNER, GOAL_NO_KR
и исключение архивных целей. Снимок первого прогона не должен менять результаты
при последующем изменении текущих данных. При переносе цели используются отдельные
поддеревья двух прогонов. Подразделение без предыдущей истории даёт null-сравнение.

Перечисленные сценарии реализованы и проверены; полный отчёт — docs/verification.md.
Тесты HTTP через сеть, Testcontainers, покрытие в процентах и нагрузочные тесты
не являются обязательными. Ошибки 404/422 и JSON проверяем при приёмке API;
при необходимости достаточно MockMvc без поднятия сервера.

## Миграции и демонстрационные данные

На изолированной PostgreSQL 15+ проверить:
- первый update создаёт схему, 24 цели в 3 подразделениях и два прогона;
- присутствуют нарушения всех четырёх правил, а также корректные и архивные цели;
- в сравнении второго с первым есть new, persisting, resolved;
- число проблем и метрики соответствуют исходным демо-данным и правилам;
- повторный update не создаёт дубликаты;
- rollback всех changeSet и повторный update проходят без ошибок;
- итоговая схема и демо-данные совпадают с первым update.

Откат Git не заменяет rollback БД. Генерация SQL и contextLoads не заменяют
применение миграций в PostgreSQL.
