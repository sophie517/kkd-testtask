# Архитектура и API

Обновлено: 2026-11-08. Описывает целевое решение. Инфраструктура и JPA-модель подготовлены;
движок правил, RunService, исторические метрики и REST API реализованы.
Полная приёмка с PostgreSQL, Docker и реальным HTTP выполнена; результаты — docs/verification.md.

## Простой монолит

Один Spring Boot сервис и один PostgreSQL. Контроллер → сервис → репозиторий.
Отдельные чистые Java-компоненты проверяют правила, считают метрики и сравнивают
множества проблем. Они не обращаются к БД, Spring или HTTP.

Сохраняем текущую структуру пакетов:
- api/controller, api/dto, api/exception — HTTP и единая обработка ошибок;
- application/service — чтение данных, транзакции, подготовка снимков и ответов;
- domain/model, domain/repository — JPA и хранение;
- validation — входные records, результаты проверки, четыре правила и их вызов;
- расчёт метрик и дельты — обычные классы рядом с сервисами, без отдельного фреймворка.

API DTO, JPA Entity и входы чистых функций разделены.
Маппинг руками через конструкторы; MapStruct и универсальные mapper-слои не нужны.
Правила можно вызывать из одного движка с явно заданными четырьмя реализациями.
Не нужны плагины правил, конфигурация правил пользователем и собственная DSL.

## Исторические данные

Модель снимков описана в 02-domain-glossary.md.
Сервис summary читает run_unit, run_goal и issue нужного и предыдущего прогонов.
При таком объёме данных достаточно загрузить снимок и обойти дерево в Java.
Обход защищён от циклов; рекурсивные SQL-запросы и кеширование не обязательны.
Все фильтры применяются до пагинации.

Создание прогона — одна транзакция с согласованным чтением исходных данных
(REPEATABLE_READ, если чтение идёт несколькими запросами).
Сначала проверяем структуру данных, выполняем правила, затем сохраняем полный результат.
Публичного endpoint запуска нет: задание требует чтение двух подготовленных прогонов.
Этап kkd-runs реализует внутренний синхронный Java-сервис запуска.
Вызывающая сторона передаёт snapshotDate и nullable previousRunId явно;
сервис не выбирает предшественника по дате и не запускается автоматически при старте.
ID нового прогона и проблем — UUID-строки, совместимые с общим строковым типом ID.
Архитектурное решение: [ADR-001](ADR/001-validation-engine-separation.md).

## GET /api/runs

Возвращает массив объектов:
id, status, snapshot_date, compared_to_run_id, issue_count.
status = COMPLETED; у первого compared_to_run_id = null.
issue_count — число проблем во всём прогоне.
Решение проекта: сортировка snapshot_date DESC, id ASC; при отсутствии данных — [].
Даты передаются как YYYY-MM-DD, поля JSON — snake_case.

## GET /api/kkd/summary?run_id=&unit_id=

Оба параметра обязательны. Поля ответа:
run {id, snapshot_date}, compared_to {id, snapshot_date} или null,
unit {id, name}, metrics, issues_by_severity, delta.
metrics содержит ровно три метрики из 01-product-context.md.
unit.name и структура поддерева берутся из снимка выбранного прогона.
Для предыдущих значений используем снимок предыдущего прогона, а не сегодняшние данные.
Формулы, направления trend и null-семантика определены в 01-product-context.md.
Проверенные примеры — examples/README.md.

## GET /api/kkd/issues

| Параметр | Требование |
|---|---|
| run_id | Обязателен |
| unit_id | Необязателен; включает дочерние подразделения снимка |
| rule_code | Необязателен; один из четырёх выбранных кодов |
| severity | Необязателен: critical / major / minor |
| limit | Целое от 1 до 100, по умолчанию 20 |
| offset | Неотрицательное целое, по умолчанию 0 |

Ответ: {items, total, limit, offset}.
Каждый item: id, run_id, rule_code, severity, goal_id, snapshot_date.
total — число записей после фильтров до пагинации. За концом списка items = [].
Сортировка rule_code ASC, goal_id ASC; уникальность пары в прогоне обеспечивает стабильность.
Фильтр minor допустим и возвращает пустой список для выбранных правил.
Правило из исходного списка, которое не выбрано для реализации, считается неизвестным кодом.

## Ошибки

Общий формат: {"error": {"code": "...", "message": "..."}}.

| Ситуация | HTTP | code |
|---|---|---|
| Прогон не существует | 404 | RUN_NOT_FOUND |
| Подразделения нет в снимке выбранного прогона | 404 | UNIT_NOT_FOUND |
| Пропущенный/пустой обязательный параметр, неизвестный код/важность, неверные limit/offset | 422 | INVALID_PARAMS |
| Неожиданная ошибка сервера | 500 | INTERNAL_ERROR |

Отсутствующий необязательный фильтр — без ограничения; переданный пустым — 422.
Скалярные параметры передаются один раз; повторы — 422.
Строковые идентификаторы не blank и не длиннее 100 символов.
Неизвестные имена параметров также отклоняются с 422, чтобы опечатки не меняли фильтры молча.
При нескольких ошибках сначала проверяем формат параметров, затем прогон,
затем подразделение. Неизвестный, но корректно оформленный строковый ID — 404.
Стандартные ошибки преобразования параметров Spring также переводим в единый JSON и 422.
Не выдаём stack trace, SQL и реквизиты подключения в ответе 500.
