# Стек, конфигурация и миграции

Обновлено: 2026-11-08.

## Выбранный стек

Задание допускает Java 17+, Spring Boot 3, PostgreSQL 15+, Maven, Liquibase/Flyway.
Оставляем уже подключённые Java 21, Spring Boot 3.5.16, Maven Wrapper,
Spring Web, Spring Data JPA, PostgreSQL driver, Liquibase YAML и JUnit 5.
Версии зависимостей берём из Spring Boot BOM.
По запросу пользователя добавлены Lombok для getters/конструкторов и springdoc 2.8.17
для Swagger UI/OpenAPI. Версия Lombok берётся из Boot BOM; annotation processing
задан явно. @Data/setters для JPA не используются.
MapStruct, Bean Validation и Testcontainers не нужны.
Параметры трёх endpoint можно проверить обычным Java-кодом.

DTO и входы чистых функций — records; в JPA простые классы.
Constructor injection, небольшие методы, понятные имена. Отдельные интерфейсы
для каждого сервиса и репозитории поверх Spring Data не создаём.

## Переменные окружения

| Переменная | Локально                                | В Docker Compose                 |
|---|-----------------------------------------|----------------------------------|
| DB_URL | jdbc:postgresql://localhost:5432/kkd_db | jdbc:postgresql://db:5432/kkd_db |
| DB_USERNAME | kkd                                     | kkd                              |
| DB_PASSWORD | Задать в окружении                      | Передать из .env                 |

Имя БД везде kkd_bd.
.env.example уже существует и содержит только демонстрационное значение.
.env исключён из Git. Spring Boot сам по себе .env не читает:
для локального запуска переменные экспортируются в shell/IDE.
Будущий Compose читает .env для подстановки, затем явно передаёт параметры приложению
через environment; наличие .env само по себе не делает переменные доступными контейнеру.
Решение для демонстрационного запуска: Compose задаёт явно обозначенные demo-defaults,
поэтому docker compose up работает и без .env. Переменные окружения позволяют
переопределить реквизиты. Приложение получает пароль от Compose, а не из fallback YAML.
Контейнерный DB_URL всегда указывает на db:5432/kkd; localhost из локального шаблона
внутрь приложения в контейнере не переносится.

## Миграции

Liquibase включён, root — classpath:db/changelog/changelog.yml.
Этап 1 создавал пустой root, этап 2 добавляет четыре changeSet схемы и демо.
Подробности — docs/domain-model.md. Применение в PostgreSQL, Hibernate validate
и полный rollback проверены на финальной приёмке.

Схема и стартовые данные управляются только Liquibase, Hibernate ddl-auto = validate.
Для каждого changeSet явно описывать rollback, включая insert и SQL CHECK.
В addForeignKeyConstraint использовать onDelete.
Все PK/FK/UNIQUE/NOT NULL и CHECK перечислять явно; remarks не создаёт ограничений.
Дочерние снимки и проблемы можно удалять каскадом при удалении прогона,
текущие КР — при удалении цели. Другие ссылки по умолчанию RESTRICT; внутри снимка связи родителя/подразделения
используют NO ACTION для проверки целостности к концу каскадной операции.
Составные FK внутри снимка обязаны включать run_id.

Демо-данные создаются миграциями: 24 цели, 3 подразделения (корень и два дочерних),
КР, справочник четырёх правил, два снимка и их проблемы с интервалом в неделю.
Включить архивные и корректные цели, нарушения всех выбранных правил,
а между прогонами — new, persisting и resolved.
Сохранённые проблемы должны совпадать с результатом Java-правил на соответствующих
демонстрационных входах; это проверяется при подготовке и тестировании fixture.
Демонстрационные входы для обоих прогонов должны быть воспроизводимыми.
После миграций текущие цели и КР соответствуют второму прогону.
Повторный старт не создаёт новые прогоны: учёт изменений обеспечивает Liquibase.

Демонстрационные прогоны уже подготовлены, поэтому runtime bootstrap с отдельным
учётом выполнения и ручное редактирование DATABASECHANGELOG не нужны.

## Запуск и проверка

- ./mvnw test — чистые unit-тесты и существующий smoke-тест.
- ./mvnw clean package — сборка.
- docker compose up — проверенный запуск: приложение, PostgreSQL, схема и демо.
- update → rollback всех changeSet → update на отдельной тестовой БД.

Dockerfile и Compose реализованы, включая PostgreSQL healthcheck
и depends_on с service_healthy. Контейнерная приёмка выполнена; отчёт — docs/verification.md.
Проверку отката не выполнять на чужой или рабочей БД.
Подробные критерии — в 06-testing-and-quality.md.
