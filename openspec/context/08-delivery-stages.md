## Зависимости

Выполняем по одному в порядке 1 → 2 → 3 → 4 → 5 → 6 → 7.
Прямые зависимости:
- project-foundation: нет.
- domain-model: project-foundation.
- validation-engine: domain-model.
- kkd-runs: domain-model, validation-engine.
- kkd-metrics-and-delta: kkd-runs.
- kkd-rest-api: kkd-metrics-and-delta.
- final-verification: kkd-rest-api.

Это зависимости реализации между changes, описанные в документах.
Статус OpenSpec ready/all_done относится к артефактам/чекбоксам отдельного change
и сам по себе не проверяет эти зависимости и не означает одобрение пользователем.

## Границы, чтобы этапы не зависели от будущего кода

1. Foundation включает Liquibase с пустым root changelog. Приложение и БД уже работают,
   но доменных таблиц ещё нет.
2. Domain-model создаёт все восемь таблиц, JPA-модель, текущие демо-данные,
   два готовых снимка и эталонные проблемы миграциями. Полные входные fixture
   обеих дат сохраняются для проверки правил.
3. Validation-engine сверяет fixture и эталонные seed-проблемы. До этого
   наличие seed не считается доказательством корректности правил.
4. Kkd-runs добавляет внутренний Java-вызов проверки и атомарного сохранения
   нового прогона. Он не создаёт ещё два demo-прогона при каждом старте.
5. Метрики читают только исторические снимки. Общий актуальный контракт
   метрик и первого прогона — в 01-product-context.md.
6. REST API добавляет три GET endpoint поверх сервисов. POST запуска,
   расписание и CRUD не входят в план.
7. Final-verification повторяет интеграционную приёмку и завершает README.
   Локальные тесты и документация уже создаются в своих этапах.

## Документы и рабочий порядок

В каждом change есть proposal.md, design.md, tasks.md.
В этапах 1–6 есть specs/<capability>/spec.md с требованиями и сценариями.
У final-verification задан skip_specs: true, поскольку это проверка и документация,
а не новая capability продукта. Его критерии — требования задания и предыдущих этапов.

Сначала пользователь просматривает планы. Для начала отдельного этапа нужна
новая команда реализовать именно его. Перед реализацией:
- перечитать текущий контекст, change и принятый результат зависимостей;
- уточнения после просмотра внести в change и затронутый общий контекст;
- не отмечать задачи выполненными до проверки;
- обновить документы и AI-PLAN.md по фактической работе;
- после завершения отдельного этапа предложить его просмотр;
- синхронизация/архивирование выполняются отдельно по выбранному workflow,
  не как побочный эффект подготовки планов.

## Приоритет источников

Исходное задание → актуальный общий контекст → согласованный change → код.
Сценарии/specs уточняют поведение; design объясняет реализацию и альтернативы;
tasks разбивает работу с проверкой каждого результата.
Если решение меняется, связанные последующие черновики обновляются перед реализацией.

Решения этой карты дополняют общий контекст:
инфраструктура включается уже на этапе 1, бизнес-схема — на этапе 2;
Compose допускает явно обозначенные demo-defaults из окружения контейнеров,
а application.yml не содержит fallback пароля.
