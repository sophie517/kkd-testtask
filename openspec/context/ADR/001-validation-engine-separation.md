# ADR-001: Отделение Validation Engine от Spring-зависимостей

## Контекст

Сервис KKD содержит 4 правила проверки качества данных (GOAL_NO_OWNER, GOAL_NO_KR, KR_WEIGHTS_SUM, CASCADE_NO_PARENT). Правила должны применяться к данным, полученным из базы, и возвращать список найденных нарушений.

## Решение

Validation Engine реализован как отдельный чистый Java-компонент, не зависящий от Spring, JPA и базы данных.

### Структура

```
validation/
├── KkdRule.java              — интерфейс правила
├── KkdRuleEngine.java        — движок применения правил
├── ValidationContext.java    — контекст данных для правил
└── impl/                     — 4 реализации правил
```

### Принцип работы

1. Service Layer получает данные из Repository.
2. Service Layer формирует `ValidationContext` — DTO с подготовленными данными.
3. `KkdRuleEngine` применяет все правила к `ValidationContext`.
4. Правила возвращают список `Issue` — чистых данных без зависимостей.
5. Service Layer сохраняет результаты и рассчитывает дельту.

### Преимущества

- **Тестируемость:** правила тестируются без Spring-контекста и базы данных.
- **Независимость:** правила не знают о Spring, JPA, HTTP.
- **Поддерживаемость:** новое правило добавляется как новая реализация `KkdRule`.
- **Прозрачность:** легко понять, что делает правило, без чтения Spring-кода.

### Альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Правила как Spring-компоненты (`@Component`) | Зависимость от Spring, сложнее тестирование |
| Правила как методы Service Layer | Смешивание логики проверок с оркестрацией |
| Правила как Spring Beans с `@Autowired` | Скрытые зависимости, сложность unit-тестирования |

## Последствия

- Validation Engine — чистый Java, без аннотаций Spring.
- DTO, Entity и модели Validation Engine разделены.
- Service Layer отвечает за маппинг данных из Repository в `ValidationContext`.
