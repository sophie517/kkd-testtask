# Тестовое задание

## Задача
Реализовать сервис модуля контроля качества данных (далее — ККД) на Java: проверку качества данных по целям и ключевым результатам, хранение результатов в PostgreSQL и REST API для страницы ККД.

---

## Требования

### 1. Схема БД
Спроектировать схему БД:
- **Подразделения** с иерархией;
- **Цели** (ответственный, родительская цель, статус, срок);
- **Ключевые результаты** (целевое и фактическое значение, вес, дата обновления факта);
- Таблицы **результатов ККД**: справочник правил, прогон и найденная проблема.

### 2. Правила проверки
Реализовать 4 правила:

| Код правила | Описание | Важность |
|---|---|---|
| `GOAL_NO_OWNER` | Цель без ответственного | critical |
| `GOAL_NO_KR` | У активной цели нет ни одного ключевого результата | critical |
| `KR_WEIGHTS_SUM` | Сумма весов КР цели не равна 100% | major |
| `CASCADE_NO_PARENT` | Цель не связана с целью вышестоящего уровня | major |

Логику правил держать **отдельно от слоя API и доступа к данным** — отдельным компонентом, который получает данные и возвращает список найденных проблем.

### 3. Стартовые данные
Загрузить стартовые данные:
- 20–30 целей в двух-трёх подразделениях;
- два прогона — так, чтобы были нарушения каждого правила и было с чем сравнивать.

### 4. Миграции
Миграции — **Liquibase** с откатом: накат → откат → повторный накат без ошибок (в проекте это условие приёмки на общем тестовом стенде).

Весь проект поднимается одной командой `docker compose up` — сервис, PostgreSQL, миграции и стартовые данные.

### 5. REST API

#### `GET /api/runs`
Список прогонов: статус, дата снимка, с каким прогоном сравнивается, число найденных проблем.

#### `GET /api/kkd/summary?run_id=&unit_id=`
Минимум три метрики по подразделению с текущим и прошлым значением, дельтой и признаком «лучше / хуже», разбивка проблем по важности и счётчики новых, сохраняющихся и исправленных. Метрики подразделения считаются с учётом дочерних, формат ответа — ниже.

#### `GET /api/kkd/issues`
Список проблем прогона с фильтрами по подразделению, правилу и важности и пагинацией (`limit`, `offset`, `total`).

### 6. Дельта
Проблема «та же самая», что и в прошлом прогоне, если совпадают **правило и объект**. У первого прогона сравнения нет — прошлые значения и дельта равны `null`, а не `0`.

### 7. Обработка ошибок
- Неизвестный прогон или подразделение — **404**;
- Некорректные параметры — **422**.

Формат ошибки единый:

```json
{"error": {"code": "...", "message": "..."}}
```

### 8. Тесты
Покрыть тестами (JUnit 5) 4 сценария:
- Два правила на граничных данных;
- Расчёт метрики;
- Расчёт дельты.
