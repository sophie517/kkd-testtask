# Продукт и объём решения

Обновлено: 2026-11-08. Источник: [_raw/business-assignment.md](_raw/business-assignment.md).

## Требования задания

Пользователи — администраторы, руководители и ответственные за целеполагание.
Нужны четыре правила из предложенных шести, PostgreSQL, история результатов,
три GET endpoint, метрики с дочерними подразделениями и сравнение прогонов.
Демонстрационные данные: 20–30 целей, 2–3 подразделения, два прогона.
Запуск всего решения одной командой docker compose up.

Еженедельная проверка описывает бизнес-процесс. Обязательный планировщик,
ручной запуск через API, интерфейс страницы и управление целями в задании не заданы.

## Решения проекта: минимальный scope

- Реализуем GOAL_NO_OWNER, GOAL_NO_KR, KR_WEIGHTS_SUM, CASCADE_NO_PARENT.
- Все правила работают только с активными целями и их КР — это требование задания.
- Одна организация, одно дерево подразделений, стабильные идентификаторы объектов.
- Готовим два завершённых демонстрационных прогона. Публичный API только читает данные.
- Код проверки — вызываемый Java-компонент. POST запуска, расписание, очередь,
  CRUD справочников, авторизация и фронтенд не входят в это решение.
- Сохранённый прогон неизменяем. Исторические ответы не используют текущие статусы
  целей или текущую структуру подразделений.

## Метрики

Поддерево подразделения определяется отдельно по снимку каждого прогона.
N — число активных целей в этом поддереве на момент прогона.
B — число различных целей с хотя бы одной проблемой. I — число проблем.

| key | title | unit | value | Улучшение |
|---|---|---|---|---|
| clean_goals_share | Доля корректных целей | % | (N − B) × 100 / N | Рост |
| goals_with_issues_count | Количество целей с проблемами | count | B | Снижение |
| issues_count | Количество проблем | count | I | Снижение |

Решение проекта: при N = 0 доля корректных целей равна 0.0%.
Доли округляем до одного знака, HALF_UP. Счётчики — целые числа.
previous — значение той же метрики в предыдущем прогоне.
delta = value − previous; для доли это процентные пункты.
Для доли delta считается из уже округлённых значений, также до одного знака.
trend: better / worse / neutral по направлению из таблицы; при delta = 0 — neutral.
Общее число активных целей используется как знаменатель, отдельной метрикой не является:
рост числа целей сам по себе не означает улучшения качества.

## Проблемы и сравнение

Ключ проблемы — пара (rule_code, goal_id). Все выбранные правила относятся к цели.
Для выбранного подразделения сначала отбираем проблемы каждого прогона в его
собственном историческом поддереве, затем сравниваем множества ключей:

- new — только в текущем;
- persisting — в обоих;
- resolved — только в предыдущем.

Перенос цели между поддеревьями может дать resolved в старом и new в новом.
Это сравнение состава проблем подразделения, не доказательство изменения самой цели.

Инварианты: current = new + persisting; previous = resolved + persisting.
Сумма счётчиков по важности равна I.
Разбивка всегда содержит critical, major, minor в этом порядке; при отсутствии — 0.
У выбранных четырёх правил minor всегда 0.

## Первый прогон и отсутствующее подразделение в прошлом

У первого прогона compared_to = null; previous, delta, trend всех метрик равны null.
В разбивке по важности previous и delta равны null.
Весь верхнеуровневый объект delta = null: счётчики new/persisting/resolved не вычисляются.

Решение проекта: если подразделение есть в текущем снимке, но отсутствует в прошлом,
compared_to всё равно указывает предыдущий прогон, а все значения сравнения
(включая верхнеуровневую delta) равны null. Отсутствие истории не подменяем нулями.
