# Ограничения сложности

Обновлено: 2026-11-08.

- Не смешивать обязательное задание и принятые нами уточнения.
- Не подгонять требования под ошибку или отсутствие реализации в коде.
- Не создавать новые миграции и бизнес-код в рамках текущего пересмотра контекста.
- Не делать авторизацию, CRUD, планировщик, очередь, микросервисы и frontend без новой задачи.
- Не добавлять две альтернативные реализации правил или миграций.
- Не использовать Spring, JPA и запросы к БД внутри правил, метрик и сравнения множеств.
- Не передавать JPA Entity в API или чистые компоненты.
- Не считать исторические значения по текущим goal/unit и не хранить только проблемные цели.
- Не использовать float/double или скрытое масштабирование Integer для процентов КР.
- Не считать new/previous/delta нулевыми при отсутствии истории.
- Не подавлять все нарушения цели из-за отсутствия КР: подавляется только KR_WEIGHTS_SUM.
- Не запрещать исходные некачественные данные, которые должны обнаруживать выбранные правила.
- Не принимать IDENTITY/BIGSERIAL за PRIMARY KEY и комментарий за ограничение.
- Не считать сборку с отключённой БД проверкой миграций.
- Не считать git revert откатом схемы PostgreSQL.
- Не логировать секреты и идентификаторы сотрудников.
- Не создавать пустые пакеты как отдельный результат: Git не сохраняет пустые директории.
- Не вводить MapStruct, DSL, универсальный rule framework или отдельный
  интерфейс для каждого класса без конкретной необходимости.
- Не поддерживать конкурирующие актуальные спецификации: задание → контекст → реализация.
