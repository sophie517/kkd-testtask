## Context

Инфраструктура, модель данных и fixture двух прогонов подготовлены.
Реализован чистый движок правил; сохранение запусков и API относятся к следующим этапам.
Этап 2 принят: данные, роли полей и fixture двух дат зафиксированы. Движок не зависит от JPA-классов и может тестироваться без БД.
Мотивация и объём: [proposal.md](proposal.md).
Контекст этапа: [этап 3](../../../context/stages/03-validation-engine.md).
Поведенческий контракт: [data-validation](specs/data-validation/spec.md).

## Goals / Non-Goals

**Goals:** обеспечить проверяемый результат этапа без зависимостей от реализации будущих этапов.
Ниже описаны выбранные проектные решения; их детали не приписываются исходному заданию.

**Non-Goals:** не создавать универсальную инфраструктуру или новые архитектурные слои,
не выполнять работу соседнего change; границы перечислены в proposal.md.


## Decisions

### 1. Вход и выход

ValidationContext содержит map/list records подразделений, всех целей и КР. Результат — rule_code, goal_id, severity; нет run_id, issue.id или даты из системных часов.

Альтернатива — передавать JPA Entity — связывает правила с persistence и lazy loading.

### 2. Организация правил

Один интерфейс правила, четыре простых реализации и движок с явно собранным списком. Движок отбирает ACTIVE цели, но контекст сохраняет архивных родителей для проверки связей.

Альтернатива — Spring-плагины или DSL — избыточна для четырёх фиксированных правил.

### 3. Границы правил

Пустой/пробельный owner считается отсутствующим. При отсутствии КР подавляется только KR_WEIGHTS_SUM. Для CASCADE нужен ACTIVE родитель в непосредственном родительском подразделении, корневые цели освобождены.

Альтернатива — пропускать все правила при отсутствии КР — скрывает другие нарушения.

### 4. Точность

BigDecimal.compareTo(100.00), без epsilon и предварительного округления суммы. 100 и 100.00 равны.

Альтернатива — equals или double — даёт ложные срабатывания из-за scale/точности.

## Risks / Trade-offs

- Родительская цель может быть архивной → в контексте нужны все цели, а не только проверяемые.
- Эталон seed может быть ошибочен → при расхождении разобраться с исходными данными и контекстом, не подгонять правило под seed.

## Migration Plan

Схема не меняется. Добавить чистую логику и тесты; выполнить ./mvnw test. Если сверка выявит ошибку seed, согласовать корректировку этапа 2 до продолжения; не переписывать уже применённые миграции молча.
