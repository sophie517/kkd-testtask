# Design

> завершены на финальной приёмке (62 теста, два Docker-стенда, HTTP,
> PostgreSQL и полный Liquibase rollback/update). Подробности — docs/verification.md.
> Описания переноса ниже сохраняют историю промежуточных этапов.


## Context

Этапы 1–6 реализованы. Документация и короткие unit/MockMvc-проверки подготовлены;
полная приёмка PostgreSQL/Docker и rollback отложена по прямому указанию пользователя.
Её результаты не заменяются успешной сборкой или mock-тестами.
Мотивация и объём: [proposal.md](proposal.md).
Контекст этапа: [этап 7](../../../context/stages/07-final-verification.md).
Новых поведенческих требований нет: skip_specs: true; приёмка сверяется с исходным заданием и этапами 1–6.

## Goals / Non-Goals

**Goals:** обеспечить воспроизводимые доказательства готовности уже реализованного решения.
Ниже описаны выбранные проектные решения; их детали не приписываются исходному заданию.

**Non-Goals:** не создавать универсальную инфраструктуру или новые архитектурные слои,
не выполнять работу соседнего change; границы перечислены в proposal.md.


## Decisions

### 1. Без новой capability

В .openspec.yaml задан skip_specs: true: приёмка и документация не вводят нового поведения системы. Вместо искусственной спецификации проверок используем исходное задание, шесть capability и матрицу в отчёте.

Альтернатива — capability 'проверить проект' — смешивает требования продукта с рабочим процессом.

### 2. Изоляция приёмки

Для чистого запуска и rollback использовать отдельный Compose project/volume/БД. Существующие данные пользователя не удалять. Зафиксировать версии Java, Maven, Docker и PostgreSQL, команды и результаты.

Альтернатива — проверять на старом volume — скрывает ошибки первого запуска и рискует данными.

### 3. Откат без новых зависимостей

Использовать официальный Liquibase CLI в одноразовом контейнере совместимой версии, с mounted changelog и подключением к изолированной БД. В README указать точную проверенную команду/версию и путь changelog. CLI-проверка не заменяется Git.

Альтернатива — добавлять runtime-зависимость или выключать Liquibase — не нужна для приёмки.

### 4. Работа с дефектами

Проверка с ошибкой остаётся невыполненной. Если нужен код, остановить соответствующий пункт, описать дефект и вернуться к отвечающему за него change; не расширять этап новой реализацией без разрешения.

Альтернатива — дописать функциональность в финальной приёмке — скрывает ответственность этапов.

### 5. Отчёт без вымышленных результатов

Записывать только реально выполненные проверки. Пропущенная из-за среды проверка явно помечается непроверенной и не закрывает обязательный критерий.

Альтернатива — считать наличие теста или YAML достаточным доказательством — не подтверждает запуск.

## Risks / Trade-offs

- Среда может не иметь Docker → записать ограничение и не объявлять финальную приёмку пройденной.
- Данные могут совпадать по количеству, но различаться по содержимому → сравнить схему, ключи и значения seed после повторного update.
- README может отставать от команд → выполнить каждую документированную команду.

## Migration Plan

Системная схема не меняется. Полный rollback выполняется только на отдельной приёмочной БД, затем update восстанавливает демонстрационное состояние. В репозитории меняются только документы отчётности; реализационные дефекты требуют возврата к соответствующему этапу.
