## Context

Модель данных и движок правил реализованы. Добавлены семь Spring Data репозиториев
и RunService; схема не менялась. Реальный rollback БД отложен пользователем.
Этапы 2 и 3 приняты, полные fixture совпадают с seed. Сервис запуска вызывается внутри Java, без внешнего управляющего API.
Мотивация и объём: [proposal.md](proposal.md).
Контекст этапа: [этап 4](../../../context/stages/04-kkd-runs.md).
Поведенческий контракт: [run-execution](specs/run-execution/spec.md).

## Goals / Non-Goals

**Goals:** обеспечить проверяемый результат этапа без зависимостей от реализации будущих этапов.
Ниже описаны выбранные проектные решения; их детали не приписываются исходному заданию.

**Non-Goals:** не создавать универсальную инфраструктуру или новые архитектурные слои,
не выполнять работу соседнего change; границы перечислены в proposal.md.
Запуск остаётся синхронным внутренним Java-вызовом, без управляющего HTTP API.

## Decisions

### 1. Явный внутренний контракт

Метод принимает snapshotDate и nullable previousRunId; ID нового прогона и проблем генерируются UUID-строками в приложении. Первый вызов может передать null. Предыдущий прогон выбирает вызывающая сторона явно, а не скрытая эвристика по дате.

Альтернатива — искать предыдущий по MAX(date) — неоднозначна при нескольких прогонах одной даты.

### 2. Одна транзакция

Чтение исходных таблиц и сохранение выполняются в одной REPEATABLE_READ транзакции. При исключении вся запись откатывается; виден только COMPLETED.

Альтернатива — сохранять RUNNING отдельно — требует сложной обработки ошибок и незавершённых состояний.

### 3. Структурная проверка

Перед движком проверить один корень, существование родителей подразделений и отсутствие циклов. Это техническая некорректность входа: запуск завершается исключением без снимка. Некачественные бизнес-данные четырёх правил пропускаются в движок.

Альтернатива — рекурсивно обходить без проверки — риск бесконечного обхода и неполного результата.

### 4. Сохранение снимка

Сохранить run, run_unit с родителями в корректном порядке, run_goal всех ACTIVE целей, затем issue. Маппинг через records. Архивные цели передаются движку как возможные родители, но не попадают в run_goal.

Альтернатива — копировать только проблемные цели — ломает знаменатель метрик.

### 5. Проверка результата

Чистые тесты проверяют оркестрацию, но не доказывают rollback БД. На изолированной PostgreSQL выполнить тест транзакции с намеренным сбоем и проверкой из нового соединения.

Альтернатива — только mock verify(repository.save) — не проверяет атомарность.

## Risks / Trade-offs

- Параллельные независимые запуски могут ссылаться на одного предшественника → v1 разрешает явное сравнение, не обещает глобальную линейную очередь.
- Чтение более одной SQL-командой может смешать версии данных → REPEATABLE_READ.
- Демо уже создаёт два прогона → новый сервис не вызывается автоматически при старте.

## Migration Plan

Новых changeSet не требуется. Добавить сервис и репозитории; на отдельной БД создать дополнительный тестовый прогон. Применённые demo-прогоны не перезаписывать и не удалять.
