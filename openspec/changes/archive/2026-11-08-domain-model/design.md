## Goals / Non-Goals

**Goals:** обеспечить проверяемый результат этапа без зависимостей от реализации будущих этапов.
Ниже описаны выбранные проектные решения; их детали не приписываются исходному заданию.

**Non-Goals:** не создавать универсальную инфраструктуру или новые архитектурные слои,
не выполнять работу соседнего change; границы перечислены в proposal.md.


## Decisions

### 1. Текущие данные и история

Создать unit, goal, key_result, kkd_rule, run, run_unit, run_goal, issue. Снимки не зависят FK от текущих goal/unit; ссылки внутри снимков составные и включают run_id.

Альтернатива — только run и issue — теряет корректные цели и историческую иерархию.

### 2. Типы и ключи

Строковые PK до 100 символов, вес NUMERIC(10,2)/BigDecimal, target/actual NUMERIC(19,2), даты DATE. kkd_rule.code — PK. Составные PK снимков можно отобразить через @EmbeddedId; простые связи допустимы через ID без тяжёлого графа JPA.

Альтернатива — числовые ID с форматированием API и масштабированный Integer — усложняет контракт.

### 3. Ограничения

Обязательные ссылки NOT NULL, goal.status ACTIVE/ARCHIVED, run.status COMPLETED, severity critical/major/minor, weight >= 0. UNIQUE(run_id,rule_code,goal_id). Явные onDelete и rollback. Ошибочный owner/сумма/уровень parent_goal допускаются для обнаружения правилами.

Альтернатива — ограничить сумму весов или уровень родителя в БД — исключает необходимые некорректные примеры.

### 4. Два прогона до движка

Liquibase загружает явно подготовленные результаты и снимки; в test resources хранятся полные входные fixture двух дат. Текущее состояние goal/KR соответствует второму. На этапе 3 Java-движок сверяет все сохранённые нарушения с эталоном; на этапе 4 проверяется путь сохранения.

Альтернатива — bootstrap через сервис запуска — создаёт зависимость этапа 2 от ещё не реализованных этапов 3–4.

### 5. Данные и откат

Разделить миграции схемы, каталога правил и демо; rollback удаляет зависимые данные до родителей и таблицы в обратном порядке. Циклы дерева проверяются подготовкой fixture, а не PostgreSQL-триггерами.

Альтернатива — один большой SQL без rollback — не удовлетворяет приёмке.

## Risks / Trade-offs

- Снимок хранит только активные цели, поэтому исходные КР первого прогона нельзя восстановить из БД → полные воспроизводимые fixture обеих дат.
- Ручные seed-нарушения могут разойтись с правилами → фиксировать ожидаемые ключи и обязательно сверить на этапе 3.

## Migration Plan

На новой PostgreSQL применить схему, каталог и seed, выполнить Hibernate validate. На отдельной тестовой БД откатить все changeSet и повторно применить; сравнить схему и данные. Прежнюю DATABASECHANGELOG не редактировать.
