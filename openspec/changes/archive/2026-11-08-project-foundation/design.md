# Design

> завершены на финальной приёмке (62 теста, два Docker-стенда, HTTP,
> PostgreSQL и полный Liquibase rollback/update). Подробности — docs/verification.md.
> Описания переноса ниже сохраняют историю промежуточных этапов.


## Context

Текущее наблюдаемое состояние репозитория: Spring Boot skeleton, один smoke-тест,
миграции удалены и Liquibase временно отключён. Код будущих этапов пока отсутствует.
Достаточно текущего skeleton. Старая схема БД не мигрируется: используем отдельную пустую БД и новый volume.
Мотивация и объём: [proposal.md](proposal.md).
Контекст этапа: [этап 1](../../../context/stages/01-project-foundation.md).
Поведенческий контракт: [project-infrastructure](specs/project-infrastructure/spec.md).

## Goals / Non-Goals

**Goals:** обеспечить проверяемый результат этапа без зависимостей от реализации будущих этапов.
Ниже описаны выбранные проектные решения; их детали не приписываются исходному заданию.

**Non-Goals:** не создавать универсальную инфраструктуру или новые архитектурные слои,
не выполнять работу соседнего change; границы перечислены в proposal.md.


## Decisions

### 1. Инфраструктура до схемы

Корневой YAML содержит databaseChangeLog: []; Liquibase включён. Это позволяет проверить wiring без преждевременного создания бизнес-таблиц.

Альтернатива — оставить Liquibase отключённым — скрывает ошибки интеграции.

### 2. Окружение контейнеров

В Compose URL приложения всегда указывает на db:5432/kkd. Локальный DB_URL из .env.example не переносим в контейнер как localhost. DB_USERNAME и DB_PASSWORD передаются явно и согласованы с POSTGRES_USER/POSTGRES_PASSWORD.

Альтернатива — один URL для хоста и контейнера — приводит к подключению не к той БД.

### 3. Запуск демо одной командой

Compose имеет явно обозначенные локальные demo-defaults для пользователя/пароля; .env позволяет их переопределить. В application.yml fallback пароля отсутствует. После клонирования docker compose up работает без обязательного копирования .env.

Альтернатива — требовать ручную подготовку окружения — делает первый запуск менее воспроизводимым.

### 4. Простой образ

Сборка JAR в многостадийном Dockerfile на JDK 21, запуск на Java 21; runtime не требует Maven. Реальные классы размещаем в пакетах при их появлении.

Альтернатива — Jib, Spring Native или классы-заглушки — не дают нужного для задания результата.

## Risks / Trade-offs

- Проверка contextLoads исключает БД → отдельно проверять фактический старт с PostgreSQL и Liquibase.
- Существующий volume может содержать старую схему → новый изолированный volume; не удалять пользовательские данные автоматически.

## Migration Plan

Добавить инфраструктурные файлы и пустой root changelog; включить Liquibase. Проверить docker compose config, сборку и два старта. Откат этапа не затрагивает бизнес-данные: доменных changeSet ещё нет; volume автоматически не удаляется.

## Review and handoff

Подход реализован и принят пользователем. Контейнерная приёмка отложена по его указанию;
сборка JAR, Docker-образа и проверка Compose выполнены.
После реализации проверить [tasks.md](tasks.md), обновить документацию и AI-PLAN.md
и передать результат на просмотр. Не переходить автоматически к следующему change.
Если согласованный результат зависимостей меняет этот дизайн, сначала обновить план.
