# Работа с ИИ-ассистентом

Обновлено: 2026-11-08. Это выбранный артефакт по требованию исходного задания.
Все семь этапов реализованы, проверены и архивированы через OpenSpec.

## Какие задачи ставились

1. Прочитать файлы проекта, контекст и исходное задание; провести аудит без исправлений.
2. После дополнения задания пользователем удалить старые миграции и противоречивые
   планы, сначала переработать контекст. Пробелы заполнить простыми решениями.
3. Через OpenSpec подготовить changes и контексты сразу для семи этапов, без реализации.
4. Реализовать project-foundation, затем domain-model, validation-engine и kkd-runs
   по последовательным командам пользователя.
5. По отдельному запросу завершить остальные этапы. На этом шаге пользователь
   просил ограничиться короткими проверками и перенести Docker/PostgreSQL на конец.
6. Последним запросом пользователь разрешил полную проверку проекта и поручил
   резюмировать работу/тесты и обновить этот файл с workflow каждого этапа.
7. После выбора пользователя «Синхронизировать specs и архивировать все семь»
   завершить OpenSpec: синхронизировать основные specs и архивировать changes.

## Пересмотр требований и контекста

Пользователь дополнил исходное задание и удалил прежние корневые
specs/design.md и specs/requirements.md. Ассистент удалил старые миграции
и два прежних плана, переработал общий контекст, ADR и контексты этапов.
Исходный текст задания при реализации не переписывался.

Как простые решения проекта выбраны строковые ID, BigDecimal для процентов,
четыре правила GOAL_NO_OWNER / GOAL_NO_KR / KR_WEIGHTS_SUM / CASCADE_NO_PARENT,
три GET endpoint и минимальные исторические снимки. Уточнены правила
каскадирования, округление, пустые поддеревья и null при отсутствии истории.
Непоследовательные числа исходного примера JSON не использованы как тестовый эталон;
согласованное демо проверяется fixture, движком и API.

## Как использовался OpenSpec

Каждый этап прошёл **change → apply → archive**:

- **change:** `openspec new change <name>`, затем proposal.md, design.md,
  tasks.md и контекст этапа. Для этапов 1–6 созданы delta-specs;
  final-verification использует `skip_specs: true`, поскольку не добавляет поведение.
- **apply:** локальный workflow openspec-apply-change: чтение status/context и
  `openspec instructions apply --change <name> --json`, реализация задач,
  проверка результатов, закрытие чекбоксов с повторной сверкой прогресса.
- **sync перед archive:** шесть delta-specs синхронизированы в openspec/specs,
  сохранив Purpose и требования/сценарии, с каноническим разделом Requirements.
  `openspec validate --specs --strict`: 6 из 6 успешно.
- **archive:** после полного завершения задач и подтверждения пользователя
  выполнен `openspec archive <name> --skip-specs --yes --json` для каждого этапа.
  Флаг skip-specs исключал повторное слияние уже синхронизированных specs;
  он не означает, что синхронизацию пропустили. У этапа 7 delta-specs отсутствуют.

Планирование, реализация и архивирование были отдельными действиями.
Тяжёлые проверки этапов 1, 2 и 4 сначала действительно откладывались;
они закрыты только на финальной приёмке 2026-11-08. Архивирование всех этапов
выполнено в конце, а не задним числом при первоначальной реализации.

и в конце полную проверку. Решения и код подготовлены ассистентом в рамках этих задач.
Пользователь явно подтвердил синхронизацию specs и archive всех семи changes.

Достоверно известно о дополнении исходного задания пользователем и удалении

поэтому авторство ручных изменений и причины не выдумываются.
