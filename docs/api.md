# REST API ККД

Контроллер: `api/controller/KkdController`. Контроллер вызывает прикладные сервисы,
а не репозитории. JPA Entity не сериализуются: ответы — отдельные records DTO.
JSON использует snake_case, даты YYYY-MM-DD, важность — critical/major/minor.
Пустые значения сравнения передаются как явный null.

## Endpoint

| Метод | Назначение | Параметры |
|---|---|---|
| GET /api/runs | Завершённые прогоны | Нет |
| GET /api/kkd/summary | Историческая сводка поддерева | run_id и unit_id обязательны |
| GET /api/kkd/issues | Проблемы прогона | run_id обязателен; unit_id, rule_code, severity, limit, offset необязательны |

GET /api/runs возвращает массив с id, status, snapshot_date, compared_to_run_id,
issue_count. Сортировка: snapshot_date DESC, id ASC. Пустой список — [].
Статус — COMPLETED, issue_count относится ко всему прогону.

Summary возвращает run, compared_to, unit, metrics, issues_by_severity и delta.
Три метрики: clean_goals_share, goals_with_issues_count, issues_count.
Названия подразделений, иерархия и состав целей берутся из выбранного снимка,
а не из текущих таблиц. Полный пример: [summary-run-002.json](examples/summary-run-002.json).

Issues возвращает {items,total,limit,offset}. Поля элемента:
id, run_id, rule_code, severity, goal_id, snapshot_date.
Фильтр подразделения включает потомков из снимка прогона.
Фильтры применяются совместно до подсчёта total и пагинации.
Сортировка: rule_code ASC, goal_id ASC.
limit: 1..100, по умолчанию 20. offset: 0..2147483647, по умолчанию 0.
За концом списка items=[], total сохраняется; переполнение offset+limit исключено.

rule_code принимает только четыре реализованных правила:
GOAL_NO_OWNER, GOAL_NO_KR, KR_WEIGHTS_SUM, CASCADE_NO_PARENT.
severity=minor допустим, но для текущих правил возвращает пустую страницу.
Пустые, повторные и неизвестные параметры отклоняются с 422.
Идентификаторы — непустые строки не длиннее 100 символов.

## Метрики и сравнение

N — число активных целей исторического поддерева; B — число различных целей
с проблемами; I — число проблем. Доля корректных целей = (N-B)*100/N;
при N=0 — 0.0. Округление HALF_UP до одного знака.
Остальные метрики — B и I. Несколько проблем одной цели увеличивают B один раз.

delta = value − previous. Дельта доли считается по округлённым значениям
в процентных пунктах. Рост доли — better, рост B/I — worse; равенство — neutral.
Разбивка по важности всегда содержит critical, major, minor в этом порядке.

Идентичность проблемы — (rule_code,goal_id), без issue.id и severity.
Перед сравнением проблемы каждого прогона отбираются по его собственному поддереву.
Перенос цели даёт resolved в старом поддереве и new в новом.
Инварианты: current=new+persisting, previous=resolved+persisting.

У первого прогона compared_to=null, весь верхнеуровневый delta=null,
previous/delta/trend метрик и previous/delta важности равны null.
Если подразделение отсутствовало в предыдущем снимке, compared_to содержит
предыдущий прогон, но значения сравнения всё равно null.
Существующее пустое подразделение имеет нулевые значения, а не отсутствующую историю.

## Ошибки

```json
{"error":{"code":"RUN_NOT_FOUND","message":"Run 'RUN-999' not found"}}
```

| HTTP | code | Причина |
|---|---|---|
| 404 | RUN_NOT_FOUND | Прогон отсутствует |
| 404 | UNIT_NOT_FOUND | Подразделения нет в снимке выбранного прогона |
| 422 | INVALID_PARAMS | Некорректные, пустые, повторные, неизвестные параметры |
| 500 | INTERNAL_ERROR | Неожиданная ошибка; внутренние детали не возвращаются |

Сначала проверяется формат всех параметров, затем существование run, затем unit.
Прочие стандартные ошибки HTTP сохраняют статус и единый error JSON.
Неподдерживаемый метод, например POST /api/runs, возвращает 405.
